System architecture

Job Search Tracker

Headless searches run daily on a schedule, one per track you've configured, verify postings against real career pages, and sync new results to a small hosted webpage — with no AI-specific tooling anywhere past the search step itself.

How it works

01 · Pipeline

Task Scheduler fires run-search.ps1 once daily per track — however many you've set up (scripts/setup-scheduler.ps1 discovers them and registers one task each). Each run invokes the Claude CLI non-interactively with a fixed, scoped tool list — no permission prompt sits waiting for a person who isn't there.

The CLI reads that track's baseline doc and resume, searches and verifies real job postings, rewrites the doc, then curls any genuinely new ones to the Worker API.

02 · Live page

The tracker page (client/) is a separate static-assets Worker deployment from the API Worker (server/) - it calls the API cross-origin over fetch, CORS-enabled on the API side. Every edit - a status change, a note - is one D1 row update, so a browser edit and a headless sync landing at the same moment can't silently overwrite each other. Either half redeploys independently of the other.

A single bearer token gates every API route; the browser stores it (and the API's URL) in localStorage after first entry.

03 · Data boundary

Everything personal — resumes, target companies, candidate profile, the prompts themselves — lives in a local private/ folder, gitignored from day one. The .claude/skills/job-search-setup/ skill generates it from a resume and a conversation, rather than anyone hand-authoring it.

Only the mechanism (scripts, server/, client/, schema) lives in the public GitHub repo, which is what makes it safe to clone onto another machine.
