System architecture

Job Search Tracker

Three headless searches run daily on a schedule, verify postings against real career pages, and sync new results to a small hosted webpage — with no AI-specific tooling anywhere past the search step itself.

How it works

01 · Pipeline

Task Scheduler fires run-search.ps1 three times a day, once per track (SWE, TPM, CPM). Each run invokes the Claude CLI non-interactively with a fixed, scoped tool list — no permission prompt sits waiting for a person who isn't there.

The CLI reads that track's baseline doc and resume, searches and verifies real job postings, rewrites the doc, then curls any genuinely new ones to the Worker.

02 · Live page

The same Worker serves the tracker webpage and answers its fetch calls. Every edit — a status change, a note — is one D1 row update, so a browser edit and a headless sync landing at the same moment can't silently overwrite each other.

A single bearer token gates every route; the browser stores it in localStorage after first entry.

03 · Data boundary

Everything that names Brenna — resumes, target companies, candidate profile, the prompts themselves — lives in a local private/ folder, gitignored from day one.

Only the mechanism (scripts, Worker source, schema) lives in the public GitHub repo, which is what makes it safe to clone onto another machine.
